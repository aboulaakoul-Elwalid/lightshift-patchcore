D7. QR5: what does the repair cost at serving time?

Registered claim. The full serving path (predict + calibrate on n ≤ 50 photos) runs within 2× vanilla latency (p95) with the bank size fixed.

What the serving path adds. Per image: one vector subtraction on a 256 × 1536 matrix (B2a) and one comparison with a stored threshold (B3). One-off, per lighting change: k forward passes to estimate the moments and the calibration scores (k = 10 or 50).

Verdict: supported. The per-image cost of the serving path is indistinguishable from vanilla (p95 ratio 0.92–1.00× over four back-to-back measurements, well inside 2×): the alignment is negligible next to the backbone and the 256 × 8000 × 1536 nearest-neighbour product. The one-off calibration costs about 0.6 s on a GPU (k = 10) and several seconds on a CPU, which is acceptable for "an operator snaps 10 photos after a lamp change".
Measurement caveats. bottle bank (8,000 × 1536), 256 px, batch size 1, 200 timed images after 20 warm-ups. The machine was shared with other jobs: the load average was above the core count (6 cores) during the CPU measurement, so the absolute CPU latencies are inflated and noisy (a re-measurement later in the night, load average 4–8, gave 307–327 ms p50 on CPU and 30–31 ms on the GPU). Only the ratio between vanilla and serving, measured back-to-back, is trustworthy. An earlier informal measurement on a quieter machine gave about 84 ms per image on CPU; do not quote either absolute CPU number as a benchmark without re-measuring on an idle machine. The raw load and thread count are stored in results/qr5/qr5.json.
